# 비주얼노벨 공통 엔진 노하우 (GARbro / msg-tool / pfs-rs 계열)

> 출처: 실전 한글화 작업 노하우에서 일반화 이식 (2026-08)

Artemis(PFS/PF8), 독자 PAK, 기타 비주얼노벨 계열 아카이브·스크립트 포맷을 다룰 때의 공통 규칙이다.

## 도구

| 도구 | 경로 규약 | 용도 |
|---|---|---|
| GARbro | `$GT_TOOLS/GARbro/<version>/` | 다수 VN 아카이브 포맷의 탐색·추출. GUI 탐색은 조사용이며, 재현 가능한 추출 단계는 CLI/스크립트로 기록 |
| msg-tool | `$GT_TOOLS/msg-tool/` | VN 스크립트/메시지 포맷의 텍스트 추출·재주입 CLI |
| pfs-rs | `$GT_TOOLS/pfs-rs/` | Artemis PFS 아카이브의 추출·리팩 CLI |

- 어떤 도구든 출력은 프로젝트의 `10_extract`, `40_build/staging` 등 명시 경로로만 보낸다.
- 리팩 도구가 있어도 **플랫폼 패키징 체인과 실기 검증이 없으면 installable build로 승격하지 않는다.**

## 엔진·아카이브 식별

- 릴리스 파일명의 엔진명을 믿지 않는다. 부트 설정(예: `system.ini`의 boot 경로·charset)과 아카이브 매직/목록으로 엔진을 확정한다.
- `root.pfs` + `root.pfs.000` 같은 **분할 아카이브 전체**를 staging 범위에 보존한다.
- 이미지·아카이브의 언어별 variant(`@Ja`, `@ZhHans` 등 접미사 계열)를 전부 열거하고, 대상 언어 슬롯과 참고용 슬롯을 구분한다.

## PFS(Artemis) 추출·리팩 검증 게이트

단일 파일 치환 proof를 만들 때의 필수 절차:

1. 입력은 manifest에 실제 등록된 `source_file`만 허용하고, 현재 프로젝트의 clean root 아래 정확한 상대 경로로 고정한다. 출력·보고서·PFS·재추출은 `40_build/staging/<proof 폴더>`에만 만든다.
2. gitignore된 clean 추출물은 `git status`로 변조를 알 수 없으므로, 입력·manifest·주입 스크립트·PFS 도구의 SHA-256을 **실행 전후로 잠근다.**
3. canonical 데이터는 **해시한 동일 raw bytes에서 파싱**한다(parse↔hash TOCTOU 차단). 파일명 inventory와 개별 해시를 실행 전후 재검증해 파일 추가·삭제를 차단한다.
4. 성공 보고에는 언어 태그 open/close/match 수, 대상 슬롯 밖 diff 0, 정확한 단일 PFS listing, 재추출 바이트 동일성을 남긴다.
5. 실기 언어 슬롯·폰트·백로그·저장/불러오기 검증 전에는 `PENDING_RUNTIME`을 유지한다.

## Artemis 다국어 scenario 처리

- scenario의 `[lang]`/`[printlang]` 그룹 수가 언어 수의 배수가 아니거나 manifest와 맞지 않으면, 줄 시작 `//`로 **줄 전체가 주석 처리된** `[lang ...]` 블록을 먼저 활성 슬롯에서 제외한다. 주석을 삭제하거나 개행을 정규화하지 말고, 같은 길이의 공백으로 마스킹한 **별도 스캔 문자열**에서만 토큰을 세고, 실제 치환 span은 오프셋이 같은 원문에서 읽어 주석 바이트와 CR/LF를 보존한다. inline `//`나 문자열 내부 토큰을 임의로 주석 취급하지 않는다.
- 주석 제외 후에도 언어 순서·그룹 수·canonical/manifest 수가 어긋나면 파서 완화나 추정으로 통과시키지 말고 데이터 불일치로 중단한다. 파서를 고쳤다면 기존 통과 입력 전체에서 group span/body와 직렬화 출력의 **바이트 동등성 회귀 검사**를 거친 뒤 새 proof를 만든다.
- 원본 active 그룹에 특정 언어 슬롯이 아예 없으면 번역문을 만들어 넣거나 포괄 허용하지 않는다. `[printlang]` 경계별 실제 slot order를 수집하고, clean source의 `source_file + segment + 안정 digest + 원문 exact`를 모두 잠근 **명시적 allowlist 한 건**으로만 결손 topology를 승인한다. 빈 문자열과 슬롯 부재를 구분한다.
- 실제 inventory에는 있지만 활성 `[lang]`·manifest row·canonical entry가 모두 0인 파일은 번역 누락으로 간주하지 말고, 다음 scenario로 점프만 하는 **stub인지** control tag·변수·점프 경로로 확인한다. stub이면 가짜 manifest 행·빈 target·원본에 없는 슬롯을 만들거나 치환 없는 no-op 리팩을 proof로 포장하지 않는다. 크기·SHA-256, 0/0/0 근거를 `N/A` 게이트 보고서에 남긴다.
- 번호형 scenario 파일이 예상 경로에 없으면 파일을 만들거나 앞뒤 번호를 추측하지 말고 clean inventory와 manifest의 실제 `source_file`을 재열거한다. `30.txt` 없이 `30_a.txt`/`30_b.txt`/`30_c.txt`가 있으면 세 파일을 권위 있는 분할 단위로 보고 각각 독립 proof를 수행한다. 분할 파일을 임의 병합하거나 별칭을 만들지 않는다.
- proof 보고서의 전역 카운터(예: manifest 전체의 서로 다른 `source_file` 수)와 현재 파일의 행 수를 혼동하지 않는다. 전역 수치가 다르다는 이유만으로 데이터 불일치로 판정하지 말고, 반대로 현재 파일의 행 수들이 서로 어긋나면 전역 필드로 정당화하지 말고 중단한다.

### 개행·제어 토큰 검증

- 모든 개행이 특정 태그(예: `[rtN]`) 바로 뒤에 있어야 한다고 가정하지 않는다. 원문과 번역문의 각 태그 뒤 개행 유무·순서와 전체 줄 수를 서로 대조한다.
- `#`로 시작하는 엔진 지시문 행은 ASCII 정규식에만 의존하지 말고 **행 전체와 순서가 원문과 정확히 같은지** 별도 검증한다.
- target에만 LF가 추가된 결함은 source·injector를 완화하지 말고 해당 target의 LF만 제거한다. 반대로 source에 있는 LF가 target에서 CRLF이거나 누락되면 그 target만 source와 같은 형태로 교정한다. 두 경우 모두 manifest와 canonical 배치를 원자적으로 함께 갱신하고, JSON의 실제 개행과 TSV escape 표기를 원시 문자열로 비교하지 말고 **실제 병합기의 디코드 규칙을 거친 값**으로 exact를 판정한다.
- 수정 후에는 기존 통과 scenario 전체와 결함 scenario를 회귀 검사한 뒤 새 proof 경로를 사용한다.

### 루비·태그 검증

- 제어 검수는 루비 태그·엔진 명령행을 별도로 보존·비교한다. 일본어 잔존 검사는 제어행과 태그 내부를 제거한 **화면 표시 문자열에만** 적용해 정상 명령·고유명사 오탐을 피한다.
- 루비·제어 태그는 뜻이 비슷해 보여도 **원문 glyph를 그대로 비교**한다. 원문 태그명과 번역된 태그명이 섞인 혼합 표기를 Review에서 차단한다.
- 루비 검수는 두 게이트로 분리한다: (1) 태그 이름·속성·개수의 원문 일치, (2) 내부 표시·독음 값의 번역 완료(가나·한자 잔존 0건). 태그 구조가 완전히 같아도 내부 값에 원문이 남으면 실패다.
- 태그의 실제 문법 glyph 순서를 확인하고 검수 정규식을 그 순서대로 작성한다. 닫힘 표기 순서를 뒤집은 정규식(예: `$]`를 `]$`로)은 오검출을 일으킨다.
- 언어 이미지의 가시 문구가 실제 runtime 동작과 충돌하거나 두 메뉴의 자막이 서로 뒤바뀐 **원본 오류**가 보이면 해당 언어 문구만 따라 번역하지 않는다. 모든 variant의 가시문자를 기록하고 원문·실제 consumer/action을 대조해 의미를 확정하며, 충돌 원본을 임의 수정하지 말고 `*_semantic_conflict`로 매니페스트에 남긴다.

## 독자 PAK / 바이너리 스크립트 처리

- **문자열 오프셋은 헤더·인덱스 메타데이터가 아니라 실제 원문 바이트 검색으로 확정한다.** 같은 길이 치환의 round-trip 성공은 가변 길이 치환의 안전성을 증명하지 않는다. 길이 필드·재배치·인덱스 갱신·전체 재검색·실기 확인을 모두 통과하기 전에는 해당 행과 빌드를 `blocked`로 유지한다.
- pair가 단위 배율 offset을 저장하는 것으로 보이면 헤더 alignment를 먼저 읽고 **모든 인접 pair**에서 `next_start_units - start_units = ceil(size_bytes/alignment)`와 zero padding을 검증한다. 이 파일별 증거가 통과한 경우에만 payload size·length word·aligned starts를 재작성하며, 규칙을 다른 PAK에 복사하지 않는다.
- 전체 문자열 열거에 **파일 전체의 무제한 UTF-16 NUL 휴리스틱 스캔을 쓰지 않는다.** 블록 범위 안에서 실제 opcode marker와 record 형태를 확인하고, `length/text/종단/다음 marker`와 블록 경계를 함께 검증하는 bounded parser를 사용한다. 장시간 전역 스캔은 시간 제한을 두고 중단한 뒤 범위를 축소한다.
- 후보를 번역문·문자열 값으로 dedupe하지 않는다. 동일 문구가 여러 블록에 반복될 수 있으므로 `(block, byte offset, span, record kind)`를 안정 키로 보존한다. 후보 보고서만 만든 단계에서는 canonical manifest·원본·빌드를 수정하지 않는다.
- 선택지는 본문과 다른 opcode·payload에 저장될 수 있다. 확인된 스크립트 구간 안에서만 opcode envelope·길이·종단자를 검증하고, payload 내부의 선택 구분자(예: `$d`)를 원형 보존해 물리 레코드와 논리 옵션 수를 각각 기록한다.
- 배치 구조 감사는 `첫 행 앞 + 행 사이 + 마지막 행 뒤`의 **모든 gap을 bounded 검사**한다. N행 배치면 N+1개 gap이다. 새 선택 payload를 찾으면 같은 사이클에서 inventory·진행률 분모·QA 근거를 바로 고친다. "전수"·"완전"이라는 표현은 검사한 블록·오프셋 범위와 경계 수를 제시할 때만 사용한다.
- gap 경계 정의는 바이트 단위로 검증한다. 한 타이틀에서는 gap 시작이 직전 본문 `terminator+3`이었고, 선행 word와 경계를 공유해 `+4`를 쓰면 gap마다 첫 1바이트가 누락됐다. 경계가 홀수 정렬일 수 있으므로 gap 전체를 문자열로 디코드하지 말고 **raw byte 패턴을 검색**한 뒤 발견 지점만 구조 분해한다. 경계 계산 오류를 발견하면 영향 범위 전체를 같은 사이클에서 재감사한다.
- 쌍둥이(중복) 블록 비교에서 **전체 raw 동일성만으로 payload 일치를 판정하지 않는다.** 블록 로컬 분기·점프 operand가 달라도 선택 문자열은 같을 수 있다. 차이가 나오면 상대 바이트 범위를 기록하고 `선행 envelope / payload / 종단 / 후행 제어부`로 분리 비교하여, payload와 종단이 exact이고 차이가 블록 로컬 제어값에 한정될 때만 근거를 남겨 승인한다.
- 반복 블록의 exact-context 증명 시 record와 record 사이 gap을 분리 비교한다. 장면 경계 gap에는 블록 이름·번호 같은 identity 바이트만 다를 수 있다. identity 필드만 바뀐 것을 증명하면 허용하되, 길이·opcode·포인터·미확인 바이트가 하나라도 다르면 자동 동기화를 중단한다.
- scratch/중간 JSON의 필드 스키마를 엄격히 파싱한다. 존재하지 않는 필드를 기본값 0으로 암묵 변환하면 전 구간 오탐이 난다. 파싱 실패·빈 값은 즉시 QA 실패로 처리한다.

## 구조화 UI 데이터 (IET 등)

- 일본어 원본 레코드와 대상 슬롯의 인덱스를 먼저 대응시킨다. 속성·분기·명령·변수는 원형으로 두고, 깨끗한 export에 번역을 적용한 뒤 staged 상태로 import·재export한다. **대상 밖 diff 0건과 레코드 수 일치**를 확인하기 전에는 원본 컨테이너를 덮어쓰지 않는다.

## 이식판·다국어판 동기화

- 다국어 이식판은 원본판에서 확정한 동일 문맥을 먼저 **exact-context sync**한다. 동기화되지 않는 이식판 전용 행만 별도 배치로 수동 번역하고, 판본별 manifest와 배치 파일을 분리한다. 동기화 보고서의 control 토큰 불일치 거부(`rejected_control_mismatch`)는 0이어야 한다.

## 이미지 sidecar·PNG 규칙

- 언어별 대응 이미지의 캔버스 치수가 달라도 다른 언어 이미지를 통째로 복사하거나 임의 resize하지 않는다. 대상 슬롯 원본의 폭·높이, alpha, PNG color type과 palette/transparency를 기록하고 유지한다. **indexed PNG는 RGBA 변환 후 저장해도 동등하지 않다.**
- 이미지와 같은 이름의 numeric CSV·좌표 TXT 같은 sidecar는 배치·슬라이스 메타데이터로 매니페스트에 묶고 기본 읽기 전용 잠금한다.
- 언어 이미지의 개별 해시가 모두 달라도 엔진 내부 공유 참조가 없다는 증거가 아니고, 반대로 같은 바이트가 여러 경로에서 발견되어도 물리 공유·동일 의미로 단정하지 않는다. exact duplicate의 모든 경로와 runtime consumer를 inventory하고, 의미가 같을 때만 원자 반영 대상으로 묶는다. 한 경로의 패치 성공을 다른 경로의 완료 증거로 쓰지 않는다.
- 투명/indexed+tRNS 이미지는 흰 배경 뷰어에서 흰 글자가 사라져 보일 수 있다. 어두운 배경 합성, alpha bbox, decoded RGBA, 팔레트를 교차 확인하고, 착시로 확인된 경우 사용한 배경과 bbox를 QA에 기록한다.
