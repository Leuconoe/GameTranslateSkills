# NSW 최종 산출물과 배포 패키징

> 출처: 실전 한글화 작업 노하우에서 일반화 이식 (2026-08)

## 전제

배포물은 사용자가 보유한 게임에 덮어쓰는 **패치 데이터만** 담는다. 원본 게임 파일, 복호화 산출물, 키는 절대 포함하지 않는다.

## 1. 최종 산출물 생성 방식

1. 각 프로젝트의 핸드오프 또는 빌드 문서에 **실제로 다시 실행할 수 있는 최종 생성 명령**을 기록한다. 깨끗한 입력 경로, staging 경로, 주입·재패킹 스크립트, 통합 순서, 검증 명령, 출력 경로를 생략하지 않는다.
2. 최종 통합 트리는 검증된 텍스트+폰트 LayeredFS를 깨끗하게 복제한 뒤, 각각 **독립 검증을 통과한** 이미지·매뉴얼 등의 번들만 덮어써서 만든다. 이전 통합 트리나 기존 ZIP을 다시 패치하지 않으며, 빌드 전 예상 파일 집합과 다른 stale 파일이 있으면 실패시킨다.
3. 하나의 릴리스 작업과 베이스 Title ID에서는 **패치 ZIP을 정확히 한 개만** 생성한다.
   - canonical 파일명은 항상 `40_build/releases/<BASE_TITLE_ID>.zip`이며, `<BASE_TITLE_ID>`는 대문자 16자리 16진수다(예: `0123456789ABCDEF.zip`).
   - 게임명·날짜·언어·버전·구성요소·준비 상태·진단용 접두사/접미사를 붙이지 않는다.
   - 표준형·SD-ready·텍스트 전용·폰트 전용·이미지 전용·진단용·단계별·루트 변형 ZIP을 병렬로 만들지 않는다. 중간·진단 빌드는 폴더와 보고서로만 유지한다.
   - 패키징 전에 단 하나의 ZIP 루트와 설치 방식을 확정하고, 검증된 canonical ZIP만 **원자적으로 교체**한다.
   - canonical ZIP은 프로젝트가 정한 최종 위치에 두며, 다른 전달·설치 폴더로의 복사·이동은 사용자의 선택이므로 자동 수행하지 않는다.
   - 여러 베이스 Title ID는 한 ZIP에 합치지 않고 Title ID별로 별도 생성한다.
4. ZIP의 최상위는 `romfs/`로 하고, 내부에 `<BASE_TITLE_ID>/romfs`를 한 번 더 넣지 않는다. 설치 문서에 이 `romfs/`가 `atmosphere/contents/<BASE_TITLE_ID>/romfs/`에 대응함을 명시한다. 프로젝트가 다른 배포 형식을 쓰면 그 정확한 루트와 설치 위치를 프로젝트 문서에 별도로 잠근다.
5. 패키징 도구는 다음을 **실패 조건**으로 검사한다.
   - 예상 번들/파일 수 불일치
   - 다른 Title ID 혼입 (0건이어야 함)
   - 깨끗한 원본과 비교한 내부 자산 identity 훼손
   - 타이틀에서 증명한 자산 ID↔외부 파일 매핑 위반 (원본에서 내부 identity와 외부 파일명이 원래 다르면 문자 동일성을 강제하지 말고 동일 외부 파일의 원본 identity 보존을 검증)
   - 수정된 컨테이너의 파싱·리로드 실패
   - 대상 변경 누락 또는 비대상 무결성 훼손
   - 필수 정적 QA 미통과
6. 생성 직후 단 하나의 정식 ZIP 파일명·크기·mtime·SHA-256을 다시 계산하고 `40_build/BUILD_MANIFEST.tsv`, `40_build/releases/SHA256SUMS.txt`, 배포 README, `50_test/TEST_LOG.md`에 **같은 값**을 기록한다. 현재 파일에서 다시 계산한 값만 유효하며 이전 해시는 폐기한다. 실기 실행이 불가능한 환경에서는 bench gate를 모두 통과시킨 뒤 실기 항목만 `PENDING (hardware)`로 남긴다.

## 2. 패키징 강제 규칙 (재발 방지)

- **최종 패키징은 문서가 아니라 빌드 스크립트의 출력명부터 canonical 규칙과 맞춘다.** 스크립트가 임시 통합명을 만들고 사람이 나중에 이름만 바꾸는 흐름은 매니페스트·README·해시 불일치를 만든다. 스크립트가 처음부터 `<BASE_TITLE_ID>.zip`을 원자적으로 생성하게 하고, 설정된 릴리스 파일명이 `^[0-9A-F]{16}\.zip$`과 다르면 즉시 실패시킨다. 정확한 파일 allowlist·ZIP root·리로드를 검사한 뒤 현재 SHA-256을 모든 릴리스 기록에 동기화한다.
- **canonical 파일명 규칙은 빌드 불변조건이다.** 빌드·릴리스 검증기는 실제 경로·basename·확장자·대소문자가 규칙과 다르면 실패하고, 임의 접두사/접미사, 중복 확장자, 빌드 뒤 수동 이름 변경, 진단·후보 ZIP의 릴리스 전달을 거부해야 한다.
- **여러 하위 시스템을 합친 최종 트리는 exact allowlist로 다시 검증한다.** 폰트·문자열·이미지 verifier가 혼합 디렉터리를 검사할 때 "추가 파일 허용"을 임의 파일 허용으로 구현하지 말고, 다른 하위 시스템의 이미 검증된 파일명 집합만 허용한다. 대상 집합 간 중복 경로 0, 누락·미등록 파일 0을 확인하고, 깨끗한 입력에서 **두 번 조립해 파일별·ZIP SHA-256 결정성**을 증명한 뒤 ZIP을 다시 열어 정렬된 entry와 payload를 전수 대조한다.
- **런타임 증거가 생긴 뒤에만 릴리스 상태를 동기화한다.** 컴파일 성공이나 ZIP 재로드 성공은 런타임 PASS가 아니다. 에뮬레이터 로그로 입력 파일, Title ID, 활성 mod, 교체 파일 수, 애플리케이션 로드를 증명하고 수정 경로별 스크린샷을 보존한 뒤 릴리스 보고서와 checksum을 갱신해, 오래된 `PENDING`·이전 해시·이전 구성요소 상태가 패키징 후 남지 않게 한다.

## 3. 릴리스 버전 관리

- 패치 릴리스 버전은 **canonical ZIP 파일명과 분리된 원장**에서 관리한다. 버전이 필요한 프로젝트는 `vMAJOR.MINOR.PATCH`, 날짜, build ID, canonical 파일, 크기, 현재 SHA-256, 에뮬레이터·실기 상태를 `40_build/RELEASE_VERSION.tsv`(또는 동등한 단일 원장)에 기록한다. canonical 파일명에는 버전 접두사·접미사를 붙이지 않는다.
- payload가 바뀌면 버전을 올리고, 깨끗한 입력에서 같은 경로로 **두 번 결정론적 빌드**를 수행한 뒤 현재 파일의 해시를 매니페스트·체크섬·설치 문서·시험 로그·핸드오프에 동기화한다.
- 문서만 바꾸거나 이전 해시를 재사용해 새 버전을 선언하지 않는다.

## 4. 완료 기준

릴리스로 인정하기 전에 다음을 모두 충족한다.

- 화면에 보이는 모든 텍스트 종류의 담당 파일과 상태가 확인됨
- 제어 코드와 자리표시자 검증 통과
- 용어집 표기 통일
- 일반·소형·선택·비활성·루비 글자에서 한글 정상 표시
- 존재하는 타이틀 화면, 설정, 저장·불러오기, 백로그, 시나리오, 매뉴얼·튜토리얼, 엔딩 경로를 **실제 항목 선택부터 번역 콘텐츠 표시와 완료·복귀까지** 시험 완료
- 최종 LayeredFS 트리에 대상 Title ID 파일만 존재
- 릴리스 ZIP을 제거했을 때 다른 게임과 원본 실행에 영향이 없음 (패치는 원본을 변경하지 않는 overlay여야 함)
