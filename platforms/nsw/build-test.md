# NSW 빌드와 실기 시험

> 출처: 실전 한글화 작업 노하우에서 일반화 이식 (2026-08)

## 1. 빌드 규칙

1. `40_build/staging`에서 **깨끗한 원본 기반**으로 빌드한다. 이미 패치된 바이너리에 누적 주입하지 않는다.
2. 이번 시험 범위에 필요한 파일만 `40_build/layeredfs/<TITLE_ID>/romfs`에 넣는다.
3. 텍스트 전용, 폰트 전용, 이미지 포함 빌드는 안정화 전까지 **별도 버전**으로 유지한다. 이미지 패치가 부팅 실패를 일으킨 전례가 있으므로 텍스트·폰트 정상 빌드와 이미지 포함 후보는 별도 폴더·별도 빌드 ID로 관리하고, 이미지 후보가 많아도 한 번에 최종 빌드에 섞지 않는다.
4. `BUILD_MANIFEST.tsv`에 입력 원본, 출력 파일, 크기, 해시, 시험 결과를 기록한다.
5. 패키징 전에 모든 패치 파일 목록과 파싱 가능 여부를 검사한다.
6. 다른 Title ID 폴더가 LayeredFS 아래에 있으면 **빌드를 폐기**하고 경로부터 수정한다.
7. 빌드 완료 후 `npm run project:validate -- --titles-root "$GT_WORKSPACE/_titles" --strict`를 실행한다.

### LayeredFS 구조

- 최종 트리는 `layeredfs/<TITLE_ID>/romfs/` 하나만 유지하고, 대상 Title ID의 파일만 존재해야 한다.
- 실기(Atmosphère)에서는 `atmosphere/contents/<BASE_TITLE_ID>/romfs/`, 에뮬레이터에서는 각자의 mod 트리(`load/<BASE_TITLE_ID>/<mod name>/romfs`)에 대응한다.
- 실패한 빌드·조사용 출력물을 정상 LayeredFS에 섞지 않는다.

### 폰트 빌드 게이트

- 첫 실기 시험은 공용 기본 본문 폰트(`$GT_TOOLS/_fonts/`에서 확인·기록한 기본 폰트) 하나만 바꾼 빌드로 진행한다. 원본이 굵기별 폰트를 참조하면 해당 굵기 슬롯에만 대응 굵기를 매핑하고, Bold를 본문 전체 기본값으로 쓰지 않는다.
- 폰트 교체는 한국어 포함 여부만으로 결정하지 않는다. 런타임이 실제로 읽는 내장 폰트 소스와 outline 형식(`glyf`/CFF), UPM·metrics, 라이선스를 확인하고, 번역문뿐 아니라 보존할 일본어/영어를 포함한 **전체 가시 코드포인트**로 후보를 평가한다. 전면 교체가 기존 glyph를 잃거나 outline 형식이 달라 병합 불가하면, 원본 glyph를 유지한 채 호환 TrueType glyph를 **추가**하는 방식을 우선한다(`cmap`/`hmtx`/`maxp` 갱신과 원본 glyph 무변경 검증 포함).
- **폰트 QA는 빌드에 들어간 바이트를 다시 꺼내 수행한다.** 작업 폴더의 TTF만 검사하지 말고 재패킹된 산출물에서 폰트 데이터를 추출해 모든 가시 코드포인트를 실제 rasterizer로 렌더링한다. tofu·빈 outline·누락 glyph 0건과 샘플 시트를 남긴다. 이는 강한 bench 증거지만 baseline·행간·루비·작은 크기 같은 실기 레이아웃 PASS를 대신하지 않는다.

## 2. 실기 시험 순서

실기 전에 `$GT_TOOLS/Eden/<version>/eden.exe`를 표준 에뮬레이터 테스트 환경으로 사용한다.

- 실행 전 에뮬레이터 mod 트리(`load/<BASE_TITLE_ID>/<mod name>/romfs`)와 현재 canonical staging 트리를 상대 경로·SHA-256으로 비교해 **누락·추가·이전 후보 잔존 파일이 0건**인지 확인한다.
- 실행 파일 경로·버전, 게임/업데이트 버전, 로케일, 활성 mod 경로와 inventory hash, 화면 캡처, 에뮬레이터 로그를 `50_test`에 기록한다.
- 에뮬레이터 PASS는 런타임 증거이지만 `PASS (hardware)`와 구분하며 실기 PASS를 대체하지 않는다.

### Eden 실행 빈도 정책

- 번역 배치·추출·병합·정적 QA를 진행할 때마다 에뮬레이터를 반복 실행하지 않는다. 중간 후보나 동일 빌드의 자동 반복 실행도 기본적으로 하지 않는다.
- 에뮬레이터 실행은 **전체 번역·독립 검수·주입·정적/라운드트립 검증과 최종 staging이 완료된 최종 후보에서 1회**, 또는 사용자가 명시적으로 요청한 경우에만 수행한다.
- 기존 로그·캡처는 실행 파일, 입력 패키지, 게임/업데이트 버전, 활성 mod와 파일별 SHA-256이 현재 대상과 exact로 일치할 때만 재사용한다. 하나라도 다르면 과거 증거로 보존하되 현재 빌드의 PASS로 승격하지 않는다.
- 다른 세션에서 에뮬레이터가 실행 중이어도 패치 주입·정적/라운드트립 검증은 중단하지 않는다. 주입 전에 현재 타이틀의 활성 mod 트리와 실행 중 세션의 대상 타이틀·mod 경로가 충돌하지 않는지 확인한다. 동일 타이틀이거나 mod 트리를 공유하면 파일 잠금·불완전 reload 위험을 기록하고 분리한 뒤 진행하며, **다른 세션의 프로세스는 종료하거나 수정하지 않는다.**

### 단계별 추가 순서 (한 번에 한 종류만)

1. 빈 LayeredFS 구조
2. 폰트만
3. 시스템·설정 문자열
4. 시나리오, 루비, 백로그, 저장·불러오기
5. 매뉴얼
6. UI 이미지
7. 통합 후보

`50_test/TEST_LOG.md`에 날짜, 빌드 ID, 게임 버전, UI/자막/보조 자막 언어, 시험 장면, 결과를 남기고 화면 증거는 `screenshots`에 둔다.

## 3. 실패 복구

- 부팅 실패 시 새 파일 추가를 중단하고 **마지막 정상 빌드로 돌아간다.**
- 아카이브를 하나씩 추가해 실패 파일을 특정한다(이진 탐색식 격리).
- 컨테이너 메타데이터, 리소스 테이블, 오프셋, 압축, 정렬을 원본과 비교한다.
- 실패한 바이너리를 다시 패치하지 않고 **깨끗한 원본에서 재빌드**한다.
- 정상 빌드 폴더를 직접 고치지 말고 버전이 붙은 새 시험 빌드를 만든다.
- 폰트 패치가 포함된 부팅 실패는 폰트를 먼저 제거해 원인을 분리한다.
- 일부 화면만 실패하면 추정한 공용 자산을 반복 수정하지 말고 **실제 소비 참조를 역추적**한다. 실패 화면의 scene/prefab, 직렬화 참조, 리소스 키, material·atlas까지 참조 사슬을 따라가고, 중복 이름 자산을 전수 inventory한 뒤 실제 런타임 소비 객체만 패치한다. 이미 통과한 화면도 같은 빌드로 다시 시험한다.

## 4. 검증기 설계 원칙 (fail-closed)

- **검증기는 입력 전제와 대상 개수를 fail-closed로 검사한다.** 잘못된 매니페스트·상태 필터·경로가 대상 0건을 만들면 반복문이 실행되지 않아 허위 PASS가 난다. canonical inventory에서 기대 행·객체·자산 수를 선언하고, 실제 승인 수가 0이거나 기대값과 다르면 콘텐츠 검사 전에 즉시 실패시킨다.
- Python의 `all(mapping.values())`처럼 **빈 집합도 참이 되는 표현을 단독 PASS 조건으로 쓰지 않는다.** expected key set 또는 정확한 invariant 수를 먼저 잠그고, 누락·추가·중복 시 값 검사 전에 실패시킨다.
- 의도적으로 빈 입력·잘못된 상태를 넣은 **negative test가 비정상 종료하는지**도 검증한다.
- 정적 QA 예외는 행 단위로 좁게 승인한다. 해당 row ID·원문·변경 구조·이유를 예외 보고서에 기록하고, 예외 baseline 밖의 새 경고는 실패시킨다. 같은 유형이라는 이유로 신규 행을 자동 승인하거나 전체 규칙을 완화하지 않는다.
- 검토 결과가 byte-identical인 **명시적 no-op도 완료 coverage에 포함**한다. 원본/출력 동일 해시, 판정 근거, 소비 경로를 기록하고 그 파일은 깨끗한 원본 그대로 유지한다. 보고서는 전체 대상·실제 변경·no-op·전체 소스·재빌드 수를 분리해 합계 보존을 검증한다.

## 5. 하드웨어가 없을 때

- 검증을 생략하지 말고 **단계별 bench 증거와 실기 항목을 분리**한다. 텍스트 슬롯 재로드, 보존 언어 exact, 내장 폰트 전수 rasterization, 이미지 대상/비대상 비교, 모든 수정 컨테이너의 파싱, CRC/로더 위험 분석, Strict 검증을 완료한다.
- 빈 구조→폰트→텍스트→이미지→통합 순서의 단계별 ZIP과 실기 runbook을 준비하고, 결과를 `PASS (bench)`와 `PENDING (hardware)`로 구분해 기록한다.

## 6. 런타임 자동화와 실기 증거 규칙

- **고정 대기시간이 아니라 화면 상태 게이트로 진행한다.** 각 입력 전에 현재 화면·선택 항목·전환 완료를 캡처나 로그로 확인하고, 입력 뒤 기대 상태가 확인되어야 다음 단계로 넘어간다. 포커스 상실·로딩 지연으로 다른 분기에 들어간 증거를 목표 경로의 PASS로 해석하지 않는다.
- **메뉴 진입을 경로 완료로 간주하지 않는다.** 목록·설정·매뉴얼·튜토리얼·저장·불러오기·종료 분기는 실제 항목 선택, 번역 콘텐츠 표시, 완료·복귀까지 시험한다. 최소한 진입 화면, 경로 내부의 대표 번역 화면, 완료·복귀 화면을 보존한다. 진행도 때문에 접근 불가하면 `PENDING`으로 둔다.
- 후반 경로 확인용 **임시 QA 상태(세이브) 변경은 원본과 완전히 분리하고 복구를 검증한다.** 대상 프로세스 종료 후 상태 파일의 모든 복제본을 inventory·해시·백업하고 최소 필드만 바꾼다. 시험 뒤 모든 복제본을 원본으로 복원해 해시 일치를 확인하고 임시 파일을 제거한다. QA 상태가 포함된 산출물은 릴리스 후보로 승인하지 않는다.
- **실기 결과를 특정 빌드에 귀속하려면 설치본과 canonical 빌드의 파일 집합·해시가 일치해야 한다.** 실행 전 설치 overlay를 inventory해 누락·잔존·추가 0건과 파일별 SHA-256 exact를 확인하고, 실행 로그에서 교체 파일 로드와 치명 오류 부재를 확인한다. 이전 후보의 잔존 파일이 있으면 화면이 정상이어도 현재 빌드의 PASS로 쓰지 않는다.
- **공유 에뮬레이터·GUI 런타임의 결과는 세션 소유권과 실제 대상이 증명될 때만 인정한다.** 소유자가 불명확한 프로세스를 전역 이름으로 강제 종료하지 않는다. 가능하면 시험 입력을 명령행 인자로 직접 전달하고, 실행 후 로그에서 입력 경로, 실제 Title ID, 활성 mod ID, 교체 파일 수, 로드 완료를 확인한다. 게임 목록 설정·활성 창 제목·사용자의 의도는 로드 증거가 아니다. 다른 타이틀·다른 파일 수·타 세션 개입이 보이면 `INVALID (cross-session)`로 기록하고 현재 패치의 실패로 귀속하지 않으며, 격리 후 같은 빌드를 재시험한다.
- 패치 주입기는 에뮬레이터 프로세스의 PID·세션·시작 시각·실행 경로를 읽기 전용으로만 기록한다. 주입 파일은 프로젝트 밖 원본을 덮어쓰지 않고 세션별 staging과 백업을 거쳐 원자적으로 교체한다. 이미 로드된 자산은 타이틀 reload 뒤에만 보일 수 있다. 주입 스크립트의 정적 해시 PASS는 런타임 PASS가 아니며, 실제 입력 경로·Title ID·활성 mod·교체 파일 수·화면 캡처를 확인할 수 없으면 `PENDING_RUNTIME`으로 남긴다.
- **이동식 미디어(SD 카드)에 LayeredFS를 쓰기 전에 볼륨 안전성을 확인한다.** 표시 이름만 믿지 말고 드라이브 문자·파일시스템·label·용량·읽기 전용 여부·health status·dirty bit를 교차 확인하고, 기존 `atmosphere/contents/<Title ID>` 트리를 읽기 전용으로 inventory한다. 경고·dirty·파일시스템 Unknown·루트 접근 실패 중 하나라도 있으면 복사·삭제를 실행하지 않는다. 백업과 사용자 승인 후 복구하고 재마운트 상태를 다시 검증한다.
- 실기 순서의 한 단계에 새 파일이 없으면 **가짜 산출물을 만들지 않는다.** 콘텐츠가 기존 자산에 분산된 경우(도움말·매뉴얼 등) 파일 inventory와 참조 근거로 독립 파일 `N/A`를 증명하고, 직전 후보와 byte-identical한 경로 전용 체크포인트를 허용한다. 실기에서는 해당 경로를 별도 행과 화면 증거로 검증한다.

## 7. 재발 방지 팁 (일반화)

- 릴리스·staging 정리 시 **파일명이나 폴더명만으로 재생성 가능성을 추정하지 않는다.** `cache`, `backup`, `staging` 같은 이름이 있어도 Git 추적 여부, 원본 입력의 실재, 대체본과의 크기·SHA-256 exact 또는 재생성 명령, canonical 릴리스 보존을 모두 확인한 대상만 exact allowlist로 삭제한다. 전제가 하나라도 어긋나면 fail-closed로 중단한다. 삭제 전 resolve한 절대 경로가 프로젝트 안에 있고 link/junction/reparse point가 없는지 확인하며, 실행 뒤 같은 정리 계획을 dry-run으로 재실행해 잔여 대상 0과 보존 anchor의 현재 해시를 기록한다.
- 아카이브 빌더가 추출 작업 트리를 보존해야 하면 **시작 전에 디스크 공간을 점검**한다(깨끗한 입력 + staging + compile + round-trip 추출 + 원자적 출력). 공간 확보를 위해 깨끗한 입력, 검증 완료 이전본, 사용자 번역 원본을 삭제하지 않는다.
- 번역하지 못한 행·해결하지 못한 실패는 빈 값이나 기존 초안으로 조용히 대체하지 않는다. `blocked` 상태와 원인, 다음 검증 조건을 매니페스트·작업 로그에 남겨 다음 사이클의 입력으로 삼는다.
- 상태값은 최소 `new`, `translated`, `reviewed`, `injected`, `device_verified`, `blocked`로 통일한다.
