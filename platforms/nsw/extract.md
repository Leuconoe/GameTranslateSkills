# NSW 추출과 엔진 분석

> 출처: 실전 한글화 작업 노하우에서 일반화 이식 (2026-08)

## 1. 기본 추출 절차

1. 유효 RomFS를 `10_extract/romfs_original`에 추출한다.
2. 추출 도구명, 버전, 전체 명령, 원본 해시를 `WORK_LOG.md`에 기록한다.
3. 확장자뿐 아니라 **파일 매직, 메타데이터, 압축 방식, 오프셋 구조**를 확인한다.
4. 엔진과 컨테이너 관계를 먼저 확정한다(예: M2 PSB/body, Ren'Py, Unity, Artemis/PFS, 독자 아카이브).
5. 디컴파일 결과는 `10_extract/decompiled`, 조사 스크립트는 `90_tools/scripts`에 둔다.
6. 재빌드에 사용하는 깨끗한 원본은 절대 수정하지 않는다. **매 빌드는 원본에서 새로 만든다.**

### 키 파일 규약 (필수)

- 복호화 키는 `$GT_TOOLS/system/prod.keys`에 둔다. **모든 nstool 명령에 `-k <prod.keys 경로>`를 명시한다.** 키를 지정하지 않으면 WARNING 후 복호화가 되지 않으며, 종료 코드만으로는 실패를 알 수 없다.
- `title.keys`는 `-k` 경로 옆에 있어도 **자동 로드되지 않는다.** 티켓이 포함된 타이틀(표준 NSP)은 패키지에서 함께 추출된 `.tik` 파일을 `--tik`으로 명시해야 콘텐츠 NCA를 복호화할 수 있다.

### 베이스 타이틀 표준 추출 절차 (NSP → NCA → RomFS)

베이스 NSP에서 유효 RomFS와 NACP까지 도달하는 실측 검증된 절차다. (업데이트 NCA는 아래 BKTR 절 참조)

```powershell
# 도구·키 (경로 규약: PLATFORM.md 도구 체인 — 버전 접미 폴더는 이름 접두로 탐색)
$ns = Join-Path (Get-ChildItem "$GT_TOOLS" -Directory -Filter 'nstool-*' |
        Select-Object -First 1).FullName 'nstool.exe'
$k  = "$GT_TOOLS\system\prod.keys"
$w  = '<프로젝트>\10_extract'

# 1) NSP 구조 확인 + PFS0 추출 (키 필수) → NCA 여러 개 + .tik/.cert
& $ns -k $k --fstree '<원본 NSP>'
& $ns -k $k -x "$w\nsp_contents" '<원본 NSP>'

# 2) 프로그램 NCA 식별: 각 NCA를 인자로 헤더를 출력해
#    "Content Type: Program" 인 NCA를 찾는다 (크기만으로 단정하지 않는다)
& $ns -k $k "$w\nsp_contents\<NCA 파일>"

# 3) 프로그램 NCA의 RomFS = partition 1 (--part1). 티켓 타이틀은 --tik 필수
& $ns -k $k --tik "$w\nsp_contents\<TitleID...>.tik" `
  --part1 "$w\romfs_original" "$w\nsp_contents\<프로그램 NCA>"

# 4) 컨트롤 NCA("Content Type: Control")의 partition 0 (--part0) → control.nacp
& $ns -k $k --tik "$w\nsp_contents\<TitleID...>.tik" `
  --part0 "$w\control" "$w\nsp_contents\<컨트롤 NCA>"
# NACP 파싱 → SupportedLanguage 목록 = 언어 슬롯 분석(§4)의 1차 근거
& $ns -k $k "$w\control\control.nacp"
```

- 각 단계의 전체 명령·종료 코드·출력 파일 수를 `WORK_LOG.md`에 기록하고, 추출 후에는 아래 "추출 성공 판정"의 검사를 적용한다.

### 엔진 식별 주의

- 릴리스 파일명에 적힌 엔진명(예: `Ren'Py`)을 실제 엔진으로 가정하지 않는다. 깨끗한 추출본의 부트 설정(예: `system.ini`의 boot 경로·charset)과 아카이브 매직/목록으로 엔진을 확정한다.
- `root.pfs`와 `root.pfs.000` 같은 **분할 아카이브는 모두** staging 범위에 보존한다.

## 2. 명령줄 도구 사용 원칙

- 추출·복호화·검증 도구는 문서화된 **CLI 명령으로만** 실행한다. GUI 창에 파일을 드래그하거나 메뉴로 추출하는 방식은 재현 불가능하므로 사용하지 않는다.
- NSP/XCI 언팩은 nstool만 사용한다(경로 규약: `$GT_TOOLS/nstool-*/nstool.exe` — 버전 접미 폴더는 이름 접두로 탐색, PLATFORM.md 도구 체인 참조). 실행 전 `--help`의 버전 배너를 확인하고, `--fstree`로 패키지 구조를 먼저 기록한 뒤 `-x`(또는 XCI 전용 옵션)로 추출한다. **모든 명령에 `-k`(§1 키 파일 규약)를 포함한다.**

```powershell
# $ns = §1 "베이스 타이틀 표준 추출 절차"에서 탐색한 nstool.exe 경로
# 구조 확인 (키 필수)
& $ns -k "$GT_TOOLS\system\prod.keys" --fstree -v '<원본 NSP/XCI>'
# 추출 (출력은 반드시 프로젝트 10_extract 아래)
& $ns -k "$GT_TOOLS\system\prod.keys" -x '<프로젝트 10_extract 출력 경로>' '<원본 NSP/XCI>'
```

- `WORK_LOG.md`에는 도구 경로와 버전, 전체 명령, 종료 코드, 표준 출력·오류 로그 위치, 입력 원본 SHA-256, 추출 파일 수와 출력 경로를 함께 기록한다.
- CLI 명령이 없거나 키·복호화 조건이 충족되지 않으면 **GUI로 우회하지 않는다.** 명령, 오류, 필요한 조건을 기록하고 `blocked` 상태로 둔 뒤 대체 가능한 CLI 경로를 조사한다.
- NxFileViewer는 CLI 인자·종료 코드·버전·입출력 경로를 확인할 수 있는 명령줄 모드만 허용한다. GUI 전용 실행이면 다른 CLI 도구를 선택한다. GUI 동작을 CLI 추출 성공으로 간주하지 않는다.
- 모든 CLI 출력물은 프로젝트의 `10_extract`, `30_translation`, `40_build`, `50_test`, `90_tools` 아래에만 생성한다.

### Windows 경로 길이 문제 복구 (subst 패턴)

CLI가 깊은 내부 경로에서 `FileStream::open()` 등 파일 열기 오류로 중단되고 원인이 경로 길이로 확인되면:

1. 패키지 손상으로 단정하거나 자산 이름을 줄이지 않는다.
2. 실패한 부분 추출물은 `10_extract` 아래 별도 이름으로 격리한다.
3. 사용 중이지 않은 드라이브 문자를 `subst <문자>: '<프로젝트 _work/<TitleID> 절대 경로>'`로 매핑한 뒤, `<문자>:\10_extract\...`처럼 짧은 출력 경로로 **동일한 CLI 명령을 처음부터** 다시 실행한다.
4. 매핑 전 기존 `subst`와 실제 볼륨 사용 여부를 확인하고, 점유된 문자를 재매핑하지 않는다. 성공·실패와 관계없이 `finally` 등으로 `subst <문자>: /D`를 실행해 해제한다.
5. `subst` 대상은 반드시 해당 프로젝트 루트여야 하며 워크스페이스 루트나 임시 공용 폴더를 가리키면 안 된다.
6. 재추출 뒤 종료 코드 0, 예상 파일 수·총크기, 핵심 파일 존재를 다시 확인한다. 정상 추출이 증명되기 전에는 실패 추출물을 삭제하지 않고, 최초 실패 경로·오류, 격리 위치, 매핑 문자·대상, 재실행 명령, 검증 결과를 `WORK_LOG.md`에 기록한다.

경로 길이 회피가 필요할 때도 **canonical 자산 이름을 자르지 않는다.** 각 원본에 충돌 없는 고정 ID를 부여해 짧은 probe 경로로 복사하고, 별도 manifest에서 ID↔원본 경로↔해시를 양방향 검증한 뒤 도구 출력을 원래 이름으로 환원한다.

### 업데이트 NCA (BKTR) 복구 패턴

- 업데이트 NCA에서 hactool의 BKTR 오류만으로 즉시 `blocked`로 확정하지 않는다. 키와 베이스 NCA가 있으면 nstool로 먼저 재현한다.

```powershell
& $ns -k "$GT_TOOLS\system\prod.keys" --titlekey <키> --basenca '<베이스 NCA>' --fstree '<업데이트 NCA>'
# 성공한 Patch RomFS는 별도 추출
& $ns -k "$GT_TOOLS\system\prod.keys" --titlekey <키> --basenca '<베이스 NCA>' -x /1 '<프로젝트 10_extract 출력>' '<업데이트 NCA>'
```

- 서명 경고·종료 코드·입력 해시를 로그에 남기고, 기본판과 적용 파일의 크기·SHA-256 일치를 확인한다.
- hactool이 해석하지 못한 raw 섹션을 정상 RomFS로 취급하지 않는다. nstool 재현마저 실패할 때만 명령·오류·해시·보존 위치를 기록해 추출 실패를 별도 차단 사유로 남긴다.
- 이 복구는 **추출 단계만** 해소한다. 이후 컨테이너 포맷의 writer 안전성·런타임 검증까지 증명한 것으로 간주하지 않는다.
- 베이스 단독 파일시스템이 비정상이고 업데이트 적용이 필수인 타이틀은 억지로 파싱하지 않는다. 베이스+업데이트의 delta/BKTR/간접 스토리지를 먼저 재구성하고 논리 크기·구간 경계·메타데이터 오프셋을 검증한다. 메타데이터가 범위를 벗어나면 추측한 오프셋으로 파일을 만들지 않는다.

### 추출 성공 판정

- **추출기의 종료 코드만 성공으로 보지 않는다.** 종료 코드 0이어도 경고 뒤 빈 폴더를 만들 수 있다. 예상 파일 수·최소 크기·컨테이너 magic·파싱·해시를 함께 검사한다.
- 같은 키로 다른 섹션이 정상 복호화되면 키 오류와 특정 포맷/도구 호환성 문제를 분리해 진단한다.
- 엔진 컨테이너 carving은 magic 검색만으로 승인하지 않는다. 선언 크기, 블록 정보 압축 해제, 데이터 블록 파싱, 내부 자산 ID를 모두 통과한 후보만 채택한다.
- 내부 파일명·의존성 문자열로 잃어버린 경로를 복구할 수 있지만 단독 증거로 쓰지 않는다. 여러 자산에서 일관된 경로 규칙과 내부 ID=출력 파일명 검증을 거치고, 추론한 부분은 작업 로그에 표시하며 실기 게이트를 유지한다.

## 3. 이전 실패 재점검 원칙

- 재개하는 타이틀은 이전 실패·중단 로그와 산출물 유무를 먼저 확인하고, **현재의** 공용 도구 경로·키 경로·입력 파일 해시로 동일 단계를 한 번 이상 재현한다.
- 실패를 즉시 `blocked`로 분류하지 않는다. 경로/인자 오류, 키 경로 이동, 도구 버전 차이, 손상·불완전 패키지, 실제 키 부족을 각각 분리해 종료 코드와 로그로 기록한다.
- 재점검이 성공하면 이전 실패를 `recovered`로 남기고 성공한 명령·도구 버전·입력 해시·출력 파일 수를 작업 로그에 연결한다. 재점검도 실패하면 원인과 다음 재현 조건을 남긴 뒤에만 차단 사유로 승격한다.
- 재점검에 GUI 우회나 임의의 다른 입력 파일을 사용하지 않는다. 입력·도구가 달라졌다면 그 차이를 별도 실험으로 기록한다.
- 외부 분석 도구가 버전·포맷 문제로 실패하면 입력을 계속 변형하지 않는다. 정확한 버전, 입력 해시, 오류를 고정하고 도구가 요구하는 전처리를 한 번 검증한다. 그래도 실패하면 재현 가능한 자체 스키마 파서나 다른 승인된 도구로 전환한다.

## 4. 언어 슬롯 확인 절차

1. 일본어, 영어, 중국어 간체·번체의 테이블과 리소스를 **키 또는 구조 위치**로 비교한다.
2. 눈에 잘 띄고 위험이 낮은 문자열 하나만 바꾼 **시험 빌드**를 만든다.
3. 실기(또는 에뮬레이터)에서 UI 언어, 자막, 보조 자막을 각각 바꾸며 실제 선택 슬롯을 기록한다.
4. 시험 문자열로 실제 소비 경로와 폰트를 확인한 뒤 전체 번역을 주입한다. **시험 문자열 몇 개의 표시는 경로 검증일 뿐 번역 완료가 아니다.**
5. 기본 정책은 **일본어 런타임 슬롯 직접 덮어쓰기**다. 일본어 시나리오·UI 레코드와 일본어 전용 이미지를 동일 ID·순서·제어 구조로 한국어화한다. 기기에 노출되지 않는 언어 슬롯(예: 중국어)에 의존하거나 그 슬롯 교체를 완료 범위로 계산하지 않는다.
6. 다른 슬롯 사용은 해당 게임에서 실기 소비가 증명되고 사용자가 예외를 승인했으며 프로젝트 지침·manifest·시험 계획에 명시된 경우로 한정한다.
7. 기존 manifest에 `approved`/`reviewed`/`translated`로 확정된 한국어 target이 있으면 다시 번역하지 않는다. 안정 ID·키·오프셋으로 대응되는 일본어 레코드에 그 값을 덮어쓰고, 번역값·제어 토큰·대응 키의 exact 검증을 수행한다. 승인 한국어가 없는 행만 신규 번역한다.

과거 다른 슬롯을 사용한 빌드와 문서는 역사적 진단 자료로만 취급하고, 새 canonical 빌드는 현행 정책으로 재검증한다.

### 언어 슬롯 순서 증명

- `ja/en/zh-*` 같은 슬롯 순서를 관례로 가정하지 않는다. 언어 인덱스, UI의 알려진 문구, 빈 슬롯, 장문 레코드 등 **여러 독립 레코드로 교차 증명**한다.
- 주입 때는 깨끗한 원본의 source identity와 현재 대상 값을 먼저 assert하고, 재로드 후 수정 슬롯 전수 일치와 보존 슬롯 byte/text exact를 별도로 검증한다.
- 대상 언어 variant가 없는 라벨은 보존 언어를 대신 수정하지 않는다. 동적 텍스트이거나 공용 fallback일 수 있으므로 참조·직렬화 텍스트를 조사하고, 그래도 대상 슬롯이 없으면 원본을 그대로 두고 실기 확인 항목으로 기록한다.

## 5. 문자열 inventory 시 주의

- 길이 접두 문자열 스캔과 인접 언어 문자열 휴리스틱은 **inventory용**이다. 배열 개수·정렬 padding·빈 언어 슬롯 때문에 오프셋이 쉽게 어긋나므로, 주입용 매니페스트는 type tree/스키마 파싱 또는 반복 레코드 전체에서 증명된 구조적 signature로 만든다. raw 후보 보고서를 canonical 번역표로 승격하지 않는다.
- 선택지가 일반 대사와 다른 opcode나 별도 길이 지정 payload에 저장될 수 있으므로, 본문 추출 행만으로 가시 문자열 inventory가 완전하다고 판단하지 않는다.
- 일부 컨테이너를 읽지 못한 상태에서 전체 커버리지를 선언하려면 정량 근거(전체 컨테이너 inventory, 읽힌 localization 구조 수, 읽지 못한 블록의 문자 분포 조사)가 필요하다. 증명할 수 없으면 `coverage unknown` 또는 `blocked`로 남긴다.
