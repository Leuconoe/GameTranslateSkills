# Handoff 규약 — 시행착오 기록과 스킬 개선 루프

> 이 스킬 세트는 실전 사용에서 발견된 갭으로 개선된다. 실제로 릴리스 전 드라이런 2회에서
> 결함 18건이 이 방식으로 발견·수정되었다. 기록되지 않은 시행착오는 다음 작업자가
> 반복한다 — **막힌 지점을 뚫었다면 그 자리에서 기록하는 것이 규칙이다.**

## 1. 기록 위치와 시점

- 각 프로젝트 루트에 `HANDOFF.md`를 둔다 (없으면 첫 기록 시 생성).
- **즉시 기록** 원칙: 다음 상황이 발생한 그 시점에 기록한다. 단계 끝에 몰아 쓰지 않는다.
  - 스킬/어댑터/엔진 문서의 지시가 실제와 다르거나 실행 불가
  - 문서에 없는 절차가 필요했음 (누락)
  - 지시가 모호해 추측으로 진행했음
  - 문서 밖 우회법·도구·명령으로 해결했음
  - 다음 작업자가 알면 시간이 절약될 노하우

## 2. 엔트리 형식 (append-only)

```markdown
## [YYYY-MM-DD] [단계/스킬명] [유형]
- 상황: 무엇을 하다가 무엇이 발생했는가 (재현 가능하게 — 명령·경로·오류 메시지)
- 원인: 파악된 원인 (미상이면 "미상"과 조사한 범위)
- 해결/우회: 실제로 통한 방법 (명령 포함)
- 문서 개선 제안: 대상 파일·섹션 + 어떤 내용을 추가/수정해야 하는가
- 상태: open | applied(반영 커밋/문서) | rejected(사유)
```

유형: `defect`(문서가 틀림) / `gap`(문서에 없음) / `ambiguity`(모호) /
`workaround`(우회) / `tip`(노하우)

## 3. 개선 반영 절차 (스킬 개선 루프)

1. **수집**: 프로젝트 완료 시(또는 사용자 요청 시) `HANDOFF.md`의 `open` 엔트리를 모은다.
2. **일반화**: 특정 게임 정보(게임명·Title ID·해시·개인 경로)를 제거하고 패턴만 추출한다
   — 지식 베이스에는 일반화된 내용만 들어간다.
3. **반영**: 대상 문서(skills/, platforms/, engines/, common/)를 수정한다.
   - 골격 어댑터(⚠️ 미검증 표시)의 실전 검증 내용은 해당 표시를 해제하며 반영
   - 문서 간 모순이 생기면 canonical 선언으로 단일화
4. **마킹**: 반영된 엔트리는 `applied` + 반영 위치를 기록. 반영하지 않기로 한 엔트리는
   `rejected` + 사유.
5. **제출**: 플러그인 저장소 사용자는 반영 diff를 저장소에 커밋하거나
   GitHub 이슈/PR로 제출한다. 커밋은 SAFETY.md의 allowlist 규칙을 따른다.

## 4. 검증 의무

- 문서 수정만으로 끝내지 않는다 — 가능하면 수정된 절차로 해당 지점을 **재실행**하여
  실제로 통하는지 확인하고, 결과를 엔트리에 남긴다 (드라이런 방식).
- 수치 기준(배치 크기, 해시, 재시도 정책)을 바꾸는 제안은 근거 데이터를 함께 기록한다.
